# 운영 안내

## 결제 모드와 권한

기본 `PAYMENT_MODE=simulation`. 이 모드의 모의 입금은 실제 자금이 아닙니다. `PAYMENT_MODE=btcpay`는 테스트넷 BTCPay 연결에 한정됩니다. 메인넷은 코드에서 차단됩니다. 실서비스 전에는 관할 운영 허가, 이용자 자격/연령, 환불·분쟁 규칙, 결과 검증 절차와 자금 보관 정책을 별도로 확정해야 합니다.

Sites가 전달하는 인증 사용자 ID로 소유권을 검사합니다. 운영 권한은 서버의 `ADMIN_EMAIL`과 로그인 이메일 일치 여부로 확인합니다. 공개 웹서버에서 임의의 사용자 헤더를 신뢰하면 안 됩니다. 로컬 서버는 모든 전달된 인증 헤더를 제거하고 로컬 모의 계정을 주입합니다.

사이트는 현재 소유자 전용입니다. 실제 다중 사용자 접근은 Sites 공유 설정에서 별도로 열어야 하며 이 작업에서는 공개로 변경하지 않습니다.

## 테스트넷 BTCPay 연결

1. 별도 테스트넷 BTCPay 인스턴스와 상점을 준비합니다.
2. 해당 테스트넷 지갑을 연결합니다. 사용자가 제공한 `bc1…` 주소는 메인넷 주소이므로 사용하지 않습니다. 복구 구문/개인키를 앱, 채팅 또는 Git에 넣지 않습니다.
3. `BTCPAY_URL`, `BTCPAY_STORE_ID`, `BTCPAY_API_KEY`, `BTCPAY_WEBHOOK_SECRET`을 Sites의 서버 비밀 환경변수로 설정합니다. 최소한 상점의 invoice 생성/조회 권한만 부여합니다. 지갑 지출 권한은 필요하지 않습니다.
4. `BTC_NETWORK=testnet`, `ESPLORA_URL=https://mempool.space/testnet/api`, `MIN_CONFIRMATIONS=3`을 설정하고 새 배포를 만듭니다.
5. `/api/webhook`에 BTCPay 웹훅을 연결합니다. 본인 전용 Sites는 플랫폼 인증을 통과해야 하므로 BTCPay의 헤더 설정에 해당 사이트 서비스 접근 자격을 넣는 구성이 필요합니다. 지원되지 않으면 사이트의 ‘입금 확인’으로 서버 재조회를 사용합니다. 현재 무인 정기 동기화는 설정되지 않았습니다.
6. 소액 테스트넷 입금으로 주소, 금액, 미달/초과, 만료 후 입금, 블록 확인, 웹훅 재전달, 정산을 검증합니다. 제공자 API는 모의 응답 테스트만으로 실제 인스턴스 호환성이 보장되지 않습니다.

웹훅은 알림일 뿐이며 서버가 BTCPay API와 블록체인을 다시 확인합니다. 동일 `(txid, vout)`를 중복 반영하지 않습니다. 확인 수 감소나 기존 거래 누락을 발견하면 그 요청을 실패시켜 정산을 중단합니다. 재조직 후 원장 복구는 자동으로 하지 않습니다.

## 지급 절차

1. 마감 후 입금 상태를 재확인하고 판정 근거를 입력해 결과를 확정합니다.
2. 운영자가 지급 목록을 묶습니다. 같은 지급은 다른 묶음에 중복 예약되지 않습니다.
3. 목록 CSV를 내려받아 수령 주소/금액을 검토한 뒤 테스트넷 지갑에서 전송합니다. 앱은 지갑 개인키를 보관하지 않으며 **자동 서명 또는 자동 송금은 구현하지 않습니다**.
4. 해당 지급 묶음에 거래 ID를 입력합니다. 서버는 출력별 주소/금액을 정확히 대조하고, 전송비를 원장에 한 번 기록합니다. 블록 확인 전에는 전송 확인 중으로 유지합니다.
5. 이미 전송한 묶음을 다시 송금하지 않습니다. 잘못된 거래 ID, RBF 대체 거래, 묶음 해제와 수령 주소 변경은 별도 운영 복구가 필요합니다. 이를 자동으로 수정하는 기능은 없습니다.

서로 다른 라운드의 지급을 하나의 거래로 합치지 마세요. 거래 하나는 한 지급 묶음에만 연결되며 전체 거래 수수료를 해당 라운드 비용에 기록합니다. 다른 용도의 출력을 섞으면 비용이 과다 귀속될 수 있습니다. 최소 전송 단위(dust) 이하의 지급은 지갑 정책에 맞는 별도 지급/누적 정책을 정하기 전 전송할 수 없습니다.

## 원장과 예외

모든 금액은 정수 satoshi. `deposits`는 관찰한 확정 입금, `bets`는 참여 신청, `payouts`는 수령 채무, `payout_batches`는 지급 묶음, `ledger`는 변경 불가 금융 이벤트, `audit`는 운영 행위입니다. 금융 이벤트를 임의 삭제/수정하지 않습니다.

늦거나 적게 보낸 금액을 유효 베팅으로 수동 전환하지 않습니다. 초과분·미달분·지연분은 환불합니다. 판정이 끝난 후 확인된 새 입금은 추가 환불 채무로 기록합니다. 대기 중인 BTCPay invoice는 만료 또는 확인된 상태가 될 때까지 정산을 막습니다.

D1 백업·복구, 운영 경보, 외부 API 장애 감시, 일일 원장 대사, 실제 지갑 잔액과 미지급 채무 비교는 운영자가 배포 환경에서 설정해야 합니다. 원장 CSV는 일부 내역의 내보내기이며 전체 DB 백업의 대체물이 아닙니다.

## 검증 범위

로컬 SQLite로 정수 계산/5% 수수료/총액 보존/중복 입금/중복 정산/권한/원장 불변성/지연 입금/지급 검증 로직을 테스트합니다. 실제 BTCPay/테스트넷 자격 정보, 실제 서명 지갑, 메인넷 운영 검증은 제공되지 않았습니다. 금융 서비스의 보안 감사나 법적 검토를 대체하지 않습니다.
